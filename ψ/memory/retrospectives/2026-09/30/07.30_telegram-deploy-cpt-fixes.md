## Honest Feedback

1. **My verification of the slip model was theater.** I benchmarked 4 models ×
   6 slips, reported JSON validity and amounts, and the user chose a model on
   that basis — but I never checked a single date. A whole category of
   production failure (the one that actually happened) was outside my test
   matrix. Benchmarks must assert every field the pipeline consumes, or say
   explicitly which fields were NOT verified.
2. **I tested in the environment I was in, not the environment I deploy to.**
   96/96 tests passing on a Bangkok-TZ host told me nothing about a UTC
   container. Time-dependent logic needs a TZ-shifted test, and I only wrote
   one because production happened to force the issue during the bug window.
   The causal test pattern (`TZ=UTC` + `setSystemTime`) should have existed
   before the first deploy, not after the first 500.
3. **Silent model retirement was predictable.** The catalog listing earlier in
   this same migration already showed qwen3:32b missing — I noticed it, but
   treated it as trivia instead of following the thread to "then the .env is
   broken right now". I had the evidence of the failure before the deploy and
   deployed anyway.

## Lessons Learned

1. Validation that depends on "today" must compare calendar dates in the
   business timezone (strings via `getBangkokDateString()`), never container-
   local `Date` objects — containers run UTC.
2. Thai slips print พ.ศ.; any pipeline consuming OCR'd Thai dates needs a
   −543 normalization guard (years ≥2400) plus prompt-level instruction.
3. AI model catalogs are mutable infrastructure. A deploy that includes an
   AI dependency should probe the configured models the way it runs
   `prisma migrate deploy` — fail loud, fail early.
4. The lucky-timing failure (bug window 00:00–07:00) is the kind that makes
   users leave: it works all day, then breaks at exactly the hour people
   record late-night expenses.
