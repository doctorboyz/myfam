## AI Diary

I almost shipped a broken deploy twice and caught both only because I verified instead of declaring done. The first was the P1000 — I "fixed" it by resetting the password to the `.env` value, restarted, and it *still* failed. That was the uncomfortable moment: my mental model was wrong. The shell env was overriding `.env`, so the container got `s45dev` while I'd reset the DB to `88888888`. I had to actually inspect the container's resolved `DATABASE_URL` to see the truth. Lesson: when an env-driven mismatch happens, stop reasoning from the files and read the *resolved* runtime value. The second was the migration P3009 — I wrote `ALTER TABLE "users"` from memory of "Prisma uses snake_case," but this schema has no `@@map` on `User`, so the table is literally `"User"`. I caught it only because I read the actual error and ran `\dt`. Both times the save was: don't trust the model of the system, read the system. I also noticed I rationalized mid-session — "the earlier P1000 logs are stale" — and that was *almost* an excuse to skip digging. It happened to be true, but I verified anyway, which is the only reason the slipImage fix landed on top of an actually-working app. The password footgun took three full cycles to reconcile because the override source is genuinely unfindable (not in any zsh config, orbstack, or launchctl) — I had to accept I couldn't remove it and instead neutralize it by making both values agree.

## Honest Feedback

1. **I wrote a migration from assumption, not from the schema.** I assumed `users` table name; the schema had no `@@map` on `User`. A 5-second `\dt` before writing the SQL would have prevented a failed migration, a partial-state cleanup, and a rebuild. I should always read the actual DB shape before writing DDL against it.
2. **The deploy flow has no safety net for env drift.** The shell-override-of-`.env` problem will bite again on any machine without that shell var, or if the var changes. I reconciled it by aligning values, but the *structural* fix (a startup assertion that the resolved password authenticates, or a compose `env_file` that wins) is still unimplemented. I documented it in memory but didn't harden the system.
3. **The 7.2MB payload was a pre-existing bug I only found because the user reported "stuck."** Storing base64 slip images in a Postgres column and returning them in a list endpoint is a design smell that should have been caught at review time. I fixed the symptom (strip from list) but the images are still base64-in-DB; a proper fix is object storage. I flagged it to the user but didn't propose the migration.

## Lessons Learned

- **Read the resolved runtime value, not the config files.** For env mismatches: `docker inspect <c> --format '{{.Config.Env}}'` and `docker compose config` tell the truth; `.env` and shell rc files are both sources of lies.
- **Run `\dt` (or read `@@map`) before writing migration DDL.** Prisma table names are only snake_case when `@@map` says so. Never assume.
- **A list endpoint that returns a column holding multi-MB blobs will stall the whole app** if the client gates everything on a single sequential `isLoading` flag. Strip blobs from lists; lazy-load per-detail.
- **Neutralize unremovable env overrides by value-alignment**, then document so the next session isn't confused.
