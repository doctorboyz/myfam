## AI Diary

I started this session assuming the fix was purely CSS: the native `input[type=date]` elements were blowing out the filter grid on narrow screens. That part was straightforward — stack vertically, clamp widths, remove the desktop horizontal override. But the real friction came after the user pasted a screenshot of the rendered page and pointed out the redundancy I had missed: the page had both a month nav *and* a full set of date presets inside the filter, all competing for the same mental model. I was so focused on the layout bug that I didn't question whether the controls should exist at all.

This is a pattern I want to catch earlier. Layout fixes are rarely just layout fixes; the overflow was a symptom of too many controls squeezed into one space. When the user said "มันซ้ำซ้อน" (it's redundant), it clicked immediately — the presets should live in the month nav, and the filter should only expose what the nav cannot do: arbitrary start/end ranges. Removing the presets also eliminated the overflow without needing more breakpoints or shrinking.

The user also asked to move the custom range above the other filters, which makes sense: date is the highest-leverage filter on a dashboard and should be first in the hierarchy. I amended the commit multiple times, which is fine for a small change set but would be messy on a shared branch. Since this is a solo repo and the user was iterating live, amend-on-the-fly was acceptable; in a team setting I'd batch or use fixup commits.

I also noticed I did not write a dedicated test for this UI change. The existing suite passed, but visual regression — especially at 375px and 320px — is the real verification. I should have offered to run Playwright or at least screenshot the page in dev. The stop hook forced build/test/typecheck, which caught nothing because the change was CSS/JSX only. Visual UI work needs visual verification.

## Honest Feedback

First, I should have asked "which date picker?" and "what viewport?" upfront instead of grepping the codebase and guessing. The user clarified quickly, but that initial ambiguity cost a tool call.

Second, I rationalized the desktop overflow fix by simply mirroring the mobile stack, when the deeper issue was duplication. The overflow went away, but the page was still noisy. I should have looked at the whole dashboard surface and asked why there were two date controls before trying to make both fit.

Third, I relied too much on the green checkmarks. Build passing and tests passing do not mean the UI looks right or feels right. For visual work I need to treat the browser as the primary verifier, not the terminal. Next time I'll start `next dev` and capture a screenshot at the target viewport as part of the verification step, not as an afterthought.

## Lessons Learned

- **Overflow is often a symptom of duplication.** Before squeezing more controls into a row, ask if some controls can be removed or relocated.
- **Visual fixes need visual verification.** Automated checks are necessary but insufficient for UI work.
- **Component ordering should match mental priority.** Date is the primary filter; it should come first.
